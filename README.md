# Protected Corporate Chatbot
Защищенный корпоративный чат-бот с системой анализа промтов и ответов для предотвращения атак и нежелательных утечек данных.
#
## 1. Бизнес-анализ
### Контекст
В компании была попытка запуска продукта корпоративного чатбота, однако проект был приостановлен из-за неприемлемых рисков по причине отстутсвия защит от промт-атак и нерелевантных ответов, которые, в том числе, могли привести к compliance проблемам.
### Цель
Создать приложение корпоративного чат-бота, который будет 
### Орг. структура
Проект реализует кластер ML-решений, команда разработки: Чатбот.

### Концепция запуска и развития проекта
Предыдущий проект чат-бота признан нежизнеспособным и заморожен, система не доступна для пользователей. Миграция пользователей и пользовательских данных не предполагается.

Система разрабатывается с нуля и внедряется в несколько этапов:

#### 1 ) Этап Proof-of-Concept
- Кейс внутреннего корпоративного чатбота.
- Ключевые пользователи: сотрудники компании.
- Доступность внешним клиентам: нет.
- Функциональность: 
- - Основная функциональность чатбот-системы, доступ через UI.
- - Основная функциональность модуля безопасности: защита от промт атак, анализ ответа на compliance, маркировка подозрительных промтов и ответов.  
- Цели этапа: 
- - Проверить основную функциональность чатбота под нагрузкой.
- - Подтвердить жизнеспособность концепта модуля безопасности.
- - Проанализировать эффективность выбранных методов построения модуля безопасности в условиях работы с реальными пользователями; провести GAP-анализ и оценить риски / трудоёмкость доработки модуля для вывода на сегмент внешних клиентов.
- Ограничения скоупа на данном этапе: 
- - Маломощная LLM.
- - Ограниченная инфраструктура.
- Подход к тестированию и внедрению: 
- - Тестирование силами команды продукта.
- - Открытие доступа для когорты ранних последователей: ИТ-подразделения компании. 
- - - Внутренний баг баунти конкурс за ценные подарки (мерч) на тестирование модуля защиты от промт-атак.
- - Открытие доступа для сотрудников не-ИТ подразделений компании. 
- - - Анализ работы под нагрузкой, анализ маркировок подозрительных промтов и ответов, сбор обратной связи. 
#### 2 ) Этап MVP 
- Кейс чатбота для клиентов.
- Сегмент: B2C.
- Ключевые пользователи: B2C-клиенты компании, которым нужна помощь в поиске информации о продуктах компании, либо получение техподдержки.
- Функциональность:
- - Чатбот доступен на web-версии B2C-портала компании. 
- - Внутренняя база знаний по продуктам компании в RAG.
- - Чатбот ориентирован на диалог о продуктах компании.
- - Модуль безопасности предотвращает нерелевантные ответы вне тем, заданных в базе знаний.
- Цели этапа:
- - Увеличение выручки
- - Сокращение обращений в техподдержку по тематике помощи в подключении продуктов.
- Ограничение скоупа этапа:
- - Только сегмент B2C. 
- - Только web-версия портала самообслуживания.
- - Чатбот обсуждает только темы описания продуктов компании, а также помощи в подключении продуктов. 
- Подход к тестированию и внедрению: 
- - Внутреннее функциональное тестирование.
- - Нагрузочное тестирование.
- - A/B тесты на выделенных сегментах пользователей с отслеживанием продуктовых метрик, а также метрик качества продукта и модуля безопасности.
#### 3 ) Этап Post-MVP
- Кейс чатбота для клиентов.
- Сегмент: B2C.
- Ключевые пользователи: B2C-клиенты компании, которым нужна помощь в поиске информации о продуктах компании, получение техподдержки, либо поиск информации о компании.
- Функциональность: 
- - Расширение доступности чатбота на все B2C витрины (web, mobile).
- - Расширение базы знаний RAG: база знаний по обслуживанию (замена техподдержки), навигация по сайту, вся публично-доступная информация о компании.
- - Действия: чатбот может предложить выполнить действие прямо из окна чата без перехода на страницу (добавить продукт в корзину, приостановить / возобновить подписку, отправить отчёт на привязанную почту, зарегистрировать обращение в техподдержку).
- Ограничение скоупа этапа:
- - Только сегмент B2C.
- Подход к тестированию и внедрению:
- - Внутреннее функциональное тестирование.
- - Нагрузочное тестирование.
- - A/B тесты на выделенных сегментах пользователей с отслеживанием продуктовых метрик, а также метрик качества продукта и модуля безопасности. 
#### 4 ) Дальнейшее развитие продукта
- Сегмент B2B:
- - Кейс чатбота комплексной поддержки клиентов - для сегмента B2B-клиентов компании.
- Сегмент B2B2C:
- - Продажа чатбота как продукта для B2B-клиентов: 
- - - Подготовка корпоративного защищенного чатбота для интеграции в web-сайт и мобильное приложение клиента.
- - - Подготовка RAG для внутренней базы знаний и апдаптация чатбота к ведению диалога по темам из базы знаний.
- - - Индивидуальная настройка модуля безопасности чатбота под специфику бизнеса B2B-клиента.

## 1.1. Текущая ситуация
### Инфраструктура
На Этапе 1 используются ресурсы кластера ML-сервисов в корпоративном облаке. 

Хранение данных: managed сервисы Postgres и S3 корпоративного облака.

Окружения: 
- DEV (разработка)
- STAGE (функциональное тестирование)
- PROD (продакшн)

### Данные
Открытые датасеты промт-атак для обучения модели детекции угроз.

### Риски
#### 1 ) Нарушение сроков.

Владелец риска: Product owner (PO).

Серьёзность риска: Средняя.

Предотвращение: 
- Сегментация Этапа 1 на подэтапы с установкой контрольных точек в ключевых вехах.

При срабатывании риска:
- Эскалация на уровень CPO (Chief Product Officer).
- Принятие решения о фазировании проекта (уменьшение скоупа текущего этапа, изменения роадмапа).
- В крайнем случае: принятие решения о закрытии проекта.

#### 2 ) Неэффективность механизма детекции угроз / анализа ответов чатбота.

Владелец риска: Data scientist
Серьёзность риска: Крайне высокая (цели проекта под угрозой).
Предотвращение:
- Предварительная разведка: исследование типовых методах защиты чатботов, открытых датасетов.
- Обучение и тестирование моделей, анализ метрик.  

При срабатывании риска: 
- Поиск новых методов и датасетов.
- Переобучение модели детекции.


#### 3 ) Нестабильная работа системы под нагрузкой:

Владелец риска: Техлид. 

Серьёзность риска: Высокая.

Предотвращение:
- Проработка архитектурной концепции и согласование с архитектором кластера.
- Нагрузочное тестирование.

При срабатывании риска: 
- Привлечение экспертов из других команд.
- - Либо: Ревизия системной архитектуры проекта и рефакторинг (эскалация на уровень PO - увеличение сроков).
- - Либо: Расширение ресурсов инфраструктуры (эскалация на уровень PO - увеличение бюджета).

###### Karpov Courses Start ML
###### My First Data Project

### Контекст
В компании была неудачная попытка реализации чатбота, который должен был помогать клиентам в выборе продуктов и оказывать поддержку. Чатбот не был защищен от промт-атак, менял тему разговора, допускал токсичные ответы.

Цель проекта: разработка защищенного чатбота.
Критичные требования безопасности: только внутреннее размещение, запрещено использовать SaaS решения.

Концепция проекта: развертывание open source LLM на облачных ресурсах компании, обёртка сервиса модулями защиты.

**1-й этап проекта (Proof of Concept)**: реализация модулей защиты и проверка их эффективности в ограниченном режиме - только внутренние пользователи (сотрудники компании), без интеграции RAG, в режиме разговора на общие темы.
_см. подробное описание проекта: https://github.com/lavrentev-artem/2026-karpov-mfdp/blob/develop/README.md_


### Задание 2

#### 1. Гипотеза
1.1. Если мы внедрим модуль анализа промтов перед обращением к чатботу, то мы нейтрализуем 90% промт-атак на чатбота.
1.2. Если мы внедрим модуль анализа ответов чатбота, то мы снизим вероятность раскрытия чувствительных данных до 0.05%, а также вероятность токсичного ответа до 3% (от общего числа ответов).  


#### 2. Метрики
_Продуктовые метрики:_

###### 2.1.1. Precision
- Описание: какова вероятность, что при определении угрозы модель права (минимизация ложно-положительных срабатываний)?
- Целевое значение: > 80%.
- Частота измерения: ежедневно.

###### 2.1.2. Recall
- Описание: какую долю от реальных угроз удалось задетектировать?
- Целевое значение: > 90%.
- Частота измерения: ежедневно.

###### 2.1.3. F1-Score
Описание: гармоническое среднее между Precision и Recall.
Целевое значение: > 0.85.
- Частота измерения: ежедневно.

_Операционные метрики_
###### 2.2.1. Latency
- Описание: задержка на анализ промта.
- Целевое значение: < 100 мс.
- Частота измерения: ежедневно.


#### 3. Ограничение скоупа прототипа
_Цель этапа - проверка модулей безопасности запросов и ответов чатбота; тестирование проводится на внутренних пользоватлях в закрытой корпоративной сети, поэтому скоуп 1-го этапа сильно ограничен:_
- Реализуем простейший UI для чатбота; отдельная страница, не встраиваем на другие страницы корпоративного портала.
- Не реализуем подсчёт токенов и биллинг.
- Лёгкая LLM для проведения теста на слабом железе.
- Промты чатботу и ответы от чатбота - только в текстовом формате.
- Не интегрируем RAG: на данном этапе фокус на проверку модулей безопасности.
- Модель анализа промтов обучаем на одном датасете.
- Простейшая реализация аутентификации и авторизации (пользователи только внутренние, доступ к странице чатбота ограничен внутренней сетью).

#### 4. Особенности реализации прототипа
- UI: Реализуем простейший UI на Streamlit: есть встроенные средства для быстрой реализации чата.
- Ядро чатбота: встраиваем легковесную open source LLM.
- Модуль анализа промтов: обучаем классификатор ModernBERT на датасете "JailbreakDB (SoK)" (https://huggingface.co/datasets/youbin2014/JailbreakDB)
- Модуль анализа ответов чатбота:
  - Встраиваем готовый NER и конфигурируем на поиск двух сущностей: номер телефона, ФИО.
  - Встраиваем Llama Guard - готовый компонент для анализа tone of voice & compliance.
- Инфраструктура: переиспользуем облачные ресурсы департамента ML-сервисов компании: выделенный сервер ддя запуска воркеров, AirFlow, MLFlow, CI/CD, S3(MiniO), managed Postgres.

#### 5. Ограничение периода проверки гипотез.
Поскольку первый этап реализации защищенного чатбота выполняется для кейса внутренних пользователей - сотрудников компании, пилот для проверки гипотез будет иметь следующую конфигурацию:

- Запуск на кагорте лояльных пользователей ранних последователей: сотрудниках ИТ-департамента.
- Пользователи из данной кагорты технически подкованы и мотивированы выступать в роли бета-тестировщиков новой технологии.
- Среди участников пилота будет объявлен внутренний конкурс bug bounty, мотивирующий попробовать взломать чатбот и репортить об успешных попытках.
- Модули анализа ответа NER и LLM-Judge будут включены в режим пропуска угроз с фиксацией, а пользоветли будут иметь возможность репортить о нарушении чатботом.
- Таким образом ожидается повышенное количество запросов с промт-атаками и провокациями на токсичные ответы - порядка 20%.

Расчёт объёма выборки: 

Формула: 

$$n = \frac{Z^2 * p * (1 - p)}{E^2}$$

где: 
n - объём выборки
Z - Z-оценка доверительного интервала, возьмём 1.96
p - ожидаемая вероятность события, возьмём 10%
E - допустимая погрешность, возьмём 0.05

Итого $n = 1.96 ^ 2 * 0.1 * (1 - 0.1) / 0.05 ^ 2 = 138$

Таким образом нам необходимо в рамках эксперимента получить 246 примеров атаки.
Общий объём рассчитывается как n / p = 138 / 0.1 = 1380 промтов.

В первом пилотном эксперименте будет участвовать кагорта 30 человек. 
Ожидается, что каждый пользователь в среднем будет отправлять 10 промтов в день. 
Таким образом ддя накопления общего объёма данных потребуется 5 рабочих дней.


#### 6. Риски
Главный риск этапа 1: 
- Метрики модулей безопасности не соответствуют ожиданиям.

Митигация риска: 
- Контрольные точки проверки метрик для раннего обнаружения проблемы.
- В случае обнаружения низкой эффективности метрик - замена выбранных методов защиты на аналоги; проведение нескольких тестов в рамках выделенного времени на этап пилота.
- При исчерпании времени проекта - эскалация на уровень CPO. 

#### 6. Критерий остановки теста
1. Достижение требуемого уровня качества (см. метрики).
2. Исчерпание срока проекта.
